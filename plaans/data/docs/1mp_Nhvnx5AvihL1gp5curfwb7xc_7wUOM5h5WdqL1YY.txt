================================================================================
NEW TECHNIQUE — COUNT RECONCILIATION BETWEEN TWO RUNS SHARING A WINDOW
================================================================================
Worth keeping, and it is the strongest deletion check this skill has had.


When two runs walk the IDENTICAL calendar window and the earlier one recorded its
instance counts, the counts can be reconciled ARITHMETICALLY rather than only by
diffing tracked IDs:


  earlier count + instances the earlier run created == later count


This run:
  SF Events  1,689 (v15, pre-write) + 4 created instances = 1,693. Observed 1,693.
  Personal     118 (v15, pre-write) + 1 created           =   119. Observed   119.
  Fun Runs      13                  + 0                   =    13. Observed    13.


Three exact matches.


WHY IT IS STRONGER THAN THE ID DIFF: the ID diff can only detect the
disappearance of events the corpus TRACKS. The count check also covers events
nobody tracked — anything ChatGPT added, anything Richard added by hand. An exact
match means nothing was removed by anyone.


CAVEAT THAT MAKES IT USABLE RATHER THAN MISLEADING: it only works when the
windows are identical AND the earlier run recorded whether its count was taken
before or after its own writes. v15 stated "run BEFORE anything was added",
which is what made the arithmetic possible. EVERY RUN SHOULD KEEP STATING THAT.
A recurring master counts as the number of INSTANCES it expands to inside the
window, not as one event — Cyberpunk Cinema contributed 2, not 1.








================================================================================
NEW FALSE-POSITIVE CLASS IN THE RECONCILIATION DIFF — CAUSE SEVEN
================================================================================
The skill lists five causes of a false-positive "deletion". v10 added a sixth (a
calendar ID matching the event-ID regex). This run found a SEVENTH, and it is
purely an artefact of how results reach the run:


  7. THE CALENDAR LISTING CAME BACK INLINE AND WAS NEVER AGGREGATED.


  Large list_events results exceed the tool-result token cap and are written to
  local files by the harness. Small ones come back inline. This run dumped the SF
  Events and Personal calendars to files, but the SF FUN RUNS calendar — only 13
  events — returned INLINE. The aggregation script globbed the saved files, so it
  never saw the fun-runs events, and ALL THIRTEEN tracked fun-run IDs appeared as
  missing.


  Thirteen apparent deletions, on the calendar that the corpus already flags as
  the one historically invisible to reconciliation. A run that trusted the script
  would have filed the entire SF Fun Runs calendar under REJECTED.


  RULE: aggregate INLINE results as well as file-dumped ones. Any per-calendar
  count under roughly 200 events will come back inline, so the small calendars —
  which are exactly the ones with the least redundancy — are the most exposed.
  Cross-check the aggregated instance count against the sum of the per-calendar
  counts before diffing anything.


  This cost one look to resolve. It would read as a catastrophic deletion event
  to a run that stopped at "not found in the dump".

================================================================================
A NEW CLASS OF SOURCE: MAIL THAT FALSIFIES WHAT THE CALENDAR ALREADY CLAIMS
================================================================================
This deserves naming because the skill has no category for it.


Every source in this corpus is a DISCOVERY source: it tells you an event exists
so you can write it down. Today Gmail produced something structurally different.


At 10:00am PT, twenty-one seconds after an Eventbrite login link, Eventbrite
confirmed that Richard's free order for Kite by the Bay had been cancelled from
his own account. The calendar event for it carried, in its description, the line
"Richard already has tickets for this — no further action needed", folded in from
a deduped copy on 2026-09-11.


That line was true when written and false four hours after v15 finished. No
discovery source could ever have caught it. Only transactional mail about
Richard's own commitments can falsify a claim already written into a calendar
description.


STANDING INSTRUCTION, new: search Gmail for from:noreply@order.eventbrite.com
alongside from:noreply@reminder.eventbrite.com every run, and reconcile any
cancellation or order change against the description of the matching calendar
event. The reminder address finds events; the order address finds out whether he
is going.


HOW IT WAS HANDLED, and why it is NOT a REJECTED entry:
  REJECTED, as this skill defines it, is for tracked events that have vanished
  from a CALENDAR. The Kite by the Bay event is untouched and still live. Richard
  gave up a ticket, not a calendar entry. Filing it under REJECTED would
  manufacture the negative taste signal that twelve reconciliations have
  correctly declined to manufacture.
  Instead the description was corrected in place with a dated block that quotes
  the superseded claim rather than deleting it — the same append-only discipline
  this corpus uses for source lines, applied to an event description.
  It IS weak evidence about taste, and it is the first of its kind. One data
  point. Do not generalise. Do not start withholding Candlestick or Bayview
  events on the strength of it.
