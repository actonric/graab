CORRECTION — THE BROWSER PREFERENCE IN THE SKILL FILE NEEDS REVISITING
================================================================
Retention v8 Part 3 records the 2026-09-10 conclusion: use Claude in Chrome
because it is Richard's real logged-in session and its site permissions are
pre-configured, whereas the desktop pane "hands out ONE-USE grants that stall an
unattended run on every navigation".


2026-09-11 contradicts BOTH halves of that. Per the append-only rule the
2026-09-10 line STAYS; this is the newer dated observation beside it.


  a. CHROME WAS NOT AVAILABLE AT ALL. The first tabs_context_mcp call returned
     "Browser extension is not connected". Not a permission issue — no bridge.


  b. THE PANE'S ONE-USE GRANT PROBLEM DID NOT OCCUR. request_access with scope
     "site" was granted once each for thefaight.com, linktr.ee and
     sunsetmercantilesf.com, and each grant held for every subsequent navigation
     to that domain for the rest of the run. Three domains, three prompts, zero
     re-requests. Instagram needed no grant at all.


  c. THE PANE WAS LOGGED IN TO INSTAGRAM. Profile pages rendered the full
     logged-in view and showed "Followed by kristenpmaher", which is the same
     signal the 2026-09-10 run used to argue Chrome was Richard's session. So
     the pane is, at minimum, signed in to an account inside Richard's circle.


  d. THE PANE'S REAL FAILURE MODE IS WORSE AND WAS NOT PREVIOUSLY RECORDED:
     it dropped the device bridge entirely, twice, mid-run. Each drop took
     Google Drive, Google Calendar, WhatsApp and every remote-devices tool with
     it. Drive and Calendar recovered; the browser pane did not come back before
     the pass ended. The run lost its final third of browser capability.


  CONSEQUENCE FOR THE SKILL FILE: "use Chrome, the pane is the fallback" is not
  reliable guidance, because on this run Chrome was simply absent. The browser
  pass needs to TRY BOTH AT MINUTE ZERO, use whichever answers, and record which.
  It should also treat a mid-run bridge drop as an expected event and finish
  writing whatever it already has rather than stalling — which is what this run
  did.


  ACTION FOR RICHARD: this is the fourth consecutive run where a browser-related
  assumption in the skill file turned out to be wrong in a new way. Worth one
  look at why the Chrome extension was not connected at 4pm Pacific on a Friday.
