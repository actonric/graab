====================================================================
NEW TOOLING CAUTION — A SILENT LOCAL OVERWRITE, AND HOW TO AVOID IT
====================================================================
This belongs beside the read_file_content warning because it is the same class of
failure: silent data loss during a document read, with no error.


Six of the thirteen live docs exceed the tool-result token cap, so the harness
writes them to local files and the run must decode them with a script. THE TRAP:
naming those local files after the document TITLE. Retention v8 Part 1 and
Retention v8 Part 2 share their first 80 title characters, so a title-truncated
filename caused Part 2 to silently overwrite Part 1 on disk. Nothing errored. A
run that did not notice would have diffed against twelve documents while
believing it had thirteen.


RULE: name local copies of these docs by DRIVE ID, never by title. Version
numbers are already known not to be unique identifiers in this corpus (five docs
titled "v4", two titled "v5"); this run establishes that TITLES are not unique
enough either, once truncated. Only the Drive ID identifies a document, on Drive
and on disk.


Corollary worth keeping: decoding those files with a short python3 script and
tail-checking on disk is CHEAPER and SAFER than reading them into context. That
should be the default pattern for the consolidated masters, not a fallback.




====================================================================
NEW FALSE-POSITIVE CLASS IN THE RECONCILIATION DIFF
====================================================================
The skill lists five causes of a false-positive "deletion". This run found a
SIXTH, and it is purely mechanical:


  6. A CALENDAR ID MATCHED THE EVENT-ID REGEX.
     2sgagcmv8ljlnfec9olvcgikeg — the local part of the SF Fun Runs calendar
     address — is 26 lowercase alphanumeric characters, exactly the shape of a
     Google Calendar event ID. Extracting tracked IDs mechanically from the
     manifest docs therefore picks it up as a tracked event, and it then appears
     "missing" from every calendar because it is not an event at all.


     Any run that extracts IDs by pattern must exclude the three calendar IDs
     explicitly. They appear in the docs constantly, by design.


     This did not cost much — it took one lookup to resolve — but it would read
     as a genuine deletion to a run that stopped at "not found on any calendar",
     and the whole point of the five-cause checklist is to stop exactly that.
     Recorded as cause six.
