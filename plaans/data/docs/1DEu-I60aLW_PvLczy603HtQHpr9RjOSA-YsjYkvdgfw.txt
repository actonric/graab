NEW FALSE-POSITIVE CLASS — the "tail check" is not sufficient on its own
================================================================================
v10 established naming local copies by Drive ID rather than by title, after two Retention
parts silently overwrote each other. That rule worked again this run. But a SECOND failure
mode in the same family was found, and it defeats the standard check:


  A TAIL CHECK CONFIRMS A DOCUMENT ENDS PLAUSIBLY. IT DOES NOT CONFIRM THE SPLIT WAS CLEAN.


Source List v12 Part 1 ends "...The Nudge, Goldstar, SF". That reads as a natural end to a
list, and v15 and v16 both recorded it as "OK" on a tail check. It is not a natural end.
Part 2 opens with a stray fragment — "Weekly, SF Bay Guardian, SF Chronicle Pink
Section/Datebook)." — before its own header. The two join: "...Goldstar, SF Weekly, SF Bay
Guardian, SF Chronicle Pink Section/Datebook)."


So the v12 split is MID-SENTENCE, contrary to that document's own claim that "the split is at
SOURCE DOCUMENT boundaries, never mid-document". NO DATA IS LOST — the content is complete
across the pair — but the claim in the header is wrong and two runs' tail checks passed it.


NEW RULE: when a family is split across parts, check that CONSECUTIVE PARTS JOIN, not merely
that each part ends plausibly. Read the last 200 characters of part N and the first 200 of
part N+1 together.




================================================================================
REUSABLE TECHNIQUES LEARNED THIS RUN
================================================================================


1. THE PRE-WRITE DUPLICATE CHECK AND THE RECONCILIATION PAGE-WALK ARE THE SAME OPERATION.
   Run the reconciliation walk first, dump every page to a local file, and the duplicate
   check then costs ZERO extra API calls — you already have every title in the window on
   disk. This run checked 25 candidate dates against 2,848 instances for free. Every run
   that does reconciliation should get its duplicate check for nothing. Do not probe.


2. CLEAR THE "DATED BEFORE THE WINDOW" FALSE POSITIVE BY OBSERVATION, NOT ARITHMETIC.
   Every previous run cleared this class by matching missing IDs to dated lines in the
   manifest PROSE. That is a check against the corpus, not against reality — if an event was
   deleted AND its manifest line said it was in the past, the deletion would be invisible.
   THIS RUN RAN A SECOND, BACKWARD LISTING over 2026-08-01 -> 2026-09-13 on all three
   calendars and matched each of the 91 missing IDs to a real live instance in that dump.
   Two extra API calls. Strictly stronger. Make it standard.


3. THE ID-EXTRACTION REGEX PICKS UP CALENDAR IDs. v15 found this; it recurred exactly as
   predicted. Google calendar IDs are 26 lowercase alphanumerics, identical in shape to event
   IDs. Exclude all three explicitly, every time:
     8b1936ddd1b6febd367e61521b43664a56f54010919d0e6ae6cbec7b877a26ab  (not 26 chars, safe)
     2sgagcmv8ljlnfec9olvcgikeg                                        (SF Fun Runs — DOES match)
   Only the Fun Runs one actually matches the regex. Exclude it by name.


4. CHECK GROUP ACTIVITY WITH list_chats, NOT BY COUNTING EMPTY MESSAGE WINDOWS.
   Four consecutive daily runs reported three WhatsApp groups "DRY, zero messages in the
   window", which reads as variance. list_chats showed the real picture: one has been silent
   for THREE MONTHS. A repeated [DRY] is not the same as a dormant source, and only
   list_chats can tell them apart. Run it on every deep pass.


5. WHEN AN EVENT IS FOUND IN A CHAT, VERIFY IT AGAINST THE ORGANISER BEFORE WRITING.
   MomCo SF was posted in COMMUNITY CHAT as a member's plug. The post gave the cadence and
   venue but not the September-to-May season, the fee structure, or the free-first-visit
   rule. doloresparkchurch.org/momcosf gave all three. The chat found it; the organiser made
   it writable. Chat posts are leads, not sources.


6. STALE CALENDAR PAGE, LIVE PER-EVENT PAGES. friendsofdubocepark.org's /calendar/ still
   shows August items and nothing for October, but /events-activities/pumpkins/ carries a
   live 2026-10-25 event the calendar omits entirely. On a site with named per-event pages,
   READ THE PER-EVENT PAGES DIRECTLY. v18 warned not to read the silence as absence; this is
   the concrete technique that acts on that warning.


7. RESIDENTS' ASSOCIATION vs MERCHANTS' ORGANISATION — CHECK BOTH.
   Hayes Valley has two organiser-side sources. hayespromenade.org carries five events and
   the Entertainment Zone that hayesvalleysf.org omits; hayesvalleysf.org carries the PROXY
   film series and the Fleet Week concert that Hayes Promenade omits. NEITHER IS A SUPERSET.
   Expect the same split in other neighbourhoods with a commercial strip.


8. A HTTP 200 IS NOT A WORKING PAGE. sfrecpark.org/Calendar.aspx returns 200 and renders
   what looks like a calendar. It is a FROZEN CACHE OF FEBRUARY 22-28, 2026, served
   regardless of the month or year requested. Fetched four ways, identical stale week every
   time. When a calendar's contents look implausible for the date, suspect a stale cache
   before suspecting the venue has no events.
